# ทดสอบ ProjectA_1 ด้วยธุรกรรมจริง: UCI Online Retail

วันที่ทดสอบ: 19 ตุลาคม 2026

แหล่งข้อมูล: Daqing Chen, *Online Retail*, UCI Machine Learning Repository (2015), [DOI 10.24432/C5BW33](https://doi.org/10.24432/C5BW33), [หน้า dataset](https://archive.ics.uci.edu/dataset/352/online%2Bretail), CC BY 4.0

## วิธีเตรียมข้อมูล

- ต้นทางมี 541,909 รายการธุรกรรม. อ่านเฉพาะ InvoiceNo, StockCode, InvoiceDate, Quantity, UnitPrice และ Country; ไม่อ่าน CustomerID หรือ Description
- จำกัดผู้ซื้อประเทศ United Kingdom, ตัด invoice ยกเลิก/คืนสินค้า, จำนวนขายและราคาที่ไม่เป็นบวก และรหัสที่ไม่ใช่สินค้าออก เหลือ 328,205 รายการในช่วง 5 เม.ย.–30 พ.ย. 2011
- เลือก 6 SKU ที่มีจำนวนวันขายสูงสุด **โดยพิจารณาเฉพาะข้อมูลก่อน 2 พ.ย.** ในกลุ่มที่มีราคา/ยอดขายตั้งแต่วันแรกและยังขายในสัปดาห์ท้ายของช่วงฝึก: `85099B`, `85123A`, `20725`, `20727`, `20728`, `22423` รวมธุรกรรมที่เลือกตลอดช่วงทดลอง 6,606 รายการ; ไม่มีการใช้ยอดขาย holdout เพื่อเลือก SKU
- รวมเป็นรายวันต่อ SKU; วันไม่มีธุรกรรมใส่จำนวนขาย 0 รวม 256 แถว และใช้ราคาที่สังเกตล่าสุด. ราคาวันที่มีหลายบิลใช้รายได้รวม ÷ จำนวนรวม
- ราคาต้นทางเป็น GBP. คูณ 40 THB/GBP **เพื่อเดโมใน UI ที่แสดงบาท**; ไม่ใช่อัตราแลกเปลี่ยนย้อนหลังหรือรายได้เงินบาทจริง
- ใช้ store เดียว `UK_ONLINE`, channel `online`; ไม่สร้างสาขาหรือหมวดหมู่ที่ต้นทางไม่มี

## ลำดับการทดสอบ

1. สมัครบัญชีองค์กรแยกต่างหากบน API/SQLite ชั่วคราว
2. ตรวจไฟล์และนำเข้าข้อมูล 5 เม.ย.–2 พ.ย. 2011 จำนวน 1,272 แถว; ไม่มีวันขาดใน 6 อนุกรม
3. เทรน XGBoost และประเมิน rolling backtest 3 จุดตัดเวลา จากนั้นสร้าง forecast 28 วัน ครบ 6/6 SKU
4. ตรวจรายงานก่อนมีข้อมูลอนาคต: ไม่มีคู่ actual ที่ตรงกับ snapshot
5. นำเข้าข้อมูลเต็มถึง 30 พ.ย. 2011 จำนวน 1,440 แถว; ระบบเก็บ snapshot เดิมและทำเครื่องหมายโมเดลเก่าเป็น `superseded`
6. ตรวจรายงานหลังนำเข้า: forecast และ actual จับคู่กันครบ 168 จาก 168 แถว (6 SKU × 28 วัน)
7. เปิด Next.js ด้วย API/ฐานข้อมูลแยกดังกล่าวใน Edge headless: login, ภาพรวมแสดงข้อมูลจริงถึง 30 พ.ย. และหน้าพยากรณ์แสดงรายงานที่บันทึกไว้ 5 ช่วงสัปดาห์; ทดสอบหน้ากว้าง 1440px และ 390px โดยไม่พบ JavaScript error หรือการล้นแนวนอน

## ผลที่วัดได้

| ช่วง | WAPE โมเดล | WAPE baseline สัปดาห์ก่อน | จำนวนแถวทดสอบ |
| --- | ---: | ---: | ---: |
| Rolling 7 วัน, 3 folds | 112.82% | 116.85% | 126 |
| Rolling 14 วัน, 3 folds | 105.66% | 99.30% | 252 |
| Rolling 28 วัน, 3 folds | 124.44% | 114.84% | 504 |
| Holdout 28 วันสุดท้าย, ไม่ใช้ฝึก | 61.16% | 72.84% | 168 |

Holdout actual รวม ฿1,617,032.80 เทียบกับ snapshot forecast ฿911,018.38 (ต่ำกว่าจริง ฿706,014.42) ค่า WAPE holdout คำนวณจากความคลาดเคลื่อนสัมบูรณ์ **ราย SKU/วัน** ไม่ใช่ผลต่างของยอดรวม. Baseline ใช้จำนวนขาย 7 วันก่อนวันตัดข้อมูลวนซ้ำและราคาล่าสุดก่อนวันตัด เช่นเดียวกับ baseline ที่ใช้ในระบบ

## ข้อสรุปและข้อจำกัด

เส้นทางข้อมูลตั้งแต่นำเข้าไปจนถึงรายงานผลภายหลังใช้งานได้ แต่ **ยังไม่ควรอ้างว่าโมเดลแม่นยำหรือพร้อมใช้ตัดสินใจทางธุรกิจ**. ผล rolling 14/28 วันแพ้ baseline และ WAPE สูงมาก; แม้ holdout สุดท้ายดีกว่า baseline ก็ยังคลาดเคลื่อน 61.16%. ไม่ได้ปรับ hyperparameter ด้วย holdout นี้ เพราะจะทำให้ผลทดสอบไม่เป็นอิสระ

หลังนำเข้ายอดจริงชุดใหม่ หน้า forecast แสดงเฉพาะกราฟยอดขายย้อนหลังและแจ้งให้เทรนใหม่ตามนโยบาย supersede; ผลพยากรณ์เก่ายังเข้าดูได้ในรายงานเทียบยอดจริง ไม่ได้แสดงเป็นโมเดลที่พร้อมพยากรณ์ปัจจุบัน

ข้อมูลนี้เป็นร้านออนไลน์ UK ช่วงปี 2011 และจำกัด 6 SKU; ไม่ครอบคลุมหลายสาขา/หมวดหมู่/ช่องทางหรือรูปแบบยอดขายของธุรกิจไทย. การมองวันที่ไม่มีธุรกรรมเป็น 0 และการตัดคืนสินค้าเป็นสมมติฐานของการทดลอง ไม่ใช่ข้อเท็จจริงสากลของทุกระบบ POS. ราคาบาทเป็นการปรับหน่วยเพื่อทดสอบหน้าจอเท่านั้น จึงห้ามนำยอดเงินนี้ไปอ้างเป็นรายได้จริงของร้าน

ทำซ้ำได้ด้วยคำสั่งใน README. สคริปต์ไม่แตะฐานข้อมูลหรือไฟล์โมเดลที่ใช้งานอยู่ และไม่เก็บไฟล์ดิบที่มี CustomerID ใน repository

## ทดสอบซ้ำบน PostgreSQL (20 ตุลาคม 2026)

รัน `scripts\real_data_e2e.py --postgres --browser` โดยใช้ฐานแยก `projecta1_test` และ Alembic revision `0001_initial` ผ่านทั้งการนำเข้า 1,440 แถว, การเทรน, forecast 28 วัน, รายงานจับคู่ 168 แถว และการเปิด UI จริงใน Edge/Playwright (login, overview, รายงาน 5 แถว, จอ 1440px/390px) ไม่พบ JavaScript error หรือแนวนอนล้นจอ ผล WAPE holdout ยังคง 61.16% เท่าเดิม ฐาน `projecta1` ไม่ถูกแตะโดยสคริปต์ทดสอบนี้

ฐานแอป `projecta1` ถูกตั้งค่าใน `backend/.env` และคัดลอกข้อมูลเดิมจาก SQLite แบบ transaction เดียว โดยเก็บไฟล์ SQLite ต้นฉบับไว้: 2 องค์กร, 1 ผู้ใช้, 1,440 แถวขาย, 18 model runs, 504 forecast snapshots. ไม่คัดลอก active sessions; ผู้ใช้ต้องล็อกอินใหม่. รหัสผ่าน PostgreSQL อยู่ใน `.env` ที่ Git ignore และไม่ได้ใส่ในรายงานนี้

## ตรวจแอปหลักและปรับโมเดล (20 ตุลาคม 2026)

ตรวจ `projecta1` แบบอ่านข้อมูลจริงผ่าน API และ Edge/Playwright: overview มี 1,440 แถว, พยากรณ์ 28 วัน, รายงาน 5 ช่วงสัปดาห์, ดาวน์โหลด CSV ได้ และไม่พบ JavaScript error. Browser smoke สร้าง session อายุสั้นสำหรับผู้ใช้เดิมแล้วลบทิ้งเมื่อจบ ไม่แก้ข้อมูลขาย

ทดลอง XGBoost แบบ Poisson (depth 3, min-child-weight 5, L2 5) เทียบกับ XGBoost เดิม, baseline รายสัปดาห์ และ baseline เฉลี่ย 4 สัปดาห์ โดยแบ่งข้อมูลฝึกสิ้นสุด 2 พ.ย. 2011; ช่วง 3–30 พ.ย. เป็น holdout ที่ไม่ใช้ฝึก:

| วิธี | Rolling WAPE 28 วัน | Holdout WAPE 28 วัน |
| --- | ---: | ---: |
| XGBoost เดิม | 124.44% | 61.16% |
| XGBoost Poisson | 100.65% | 56.77% |
| ยอดสัปดาห์ก่อน | 114.84% | 72.84% |
| เฉลี่ย 4 สัปดาห์ตามวันในสัปดาห์ | 98.00% | 68.51% |

Poisson ดีขึ้นกว่ารุ่นเดิมทั้ง rolling และ holdout ของชุดข้อมูลนี้ แต่ baseline เฉลี่ย 4 สัปดาห์ยังดีกว่าเล็กน้อยใน rolling validation และ **56.77% ยังคลาดเคลื่อนสูง**. ไม่ควรอ้างว่าพร้อมใช้ตัดสินใจธุรกิจโดยไม่ทดสอบข้อมูลของธุรกิจนั้นเอง. รันซ้ำได้ด้วย `backend/scripts/benchmark_models.py` ซึ่งอ่านฐานหลักอย่างเดียว ไม่บันทึกโมเดล

หลัง unit tests 9/9 และ E2E บน `projecta1_test` ผ่าน จึงเทรน Poisson รุ่นใหม่ใน `projecta1` เป็น run 20 โดยยังเก็บยอดขาย 1,440 แถวและประวัติ forecast เดิมไว้. รุ่นใหม่มี WAPE rolling 28 วัน 72.67% เมื่อฝึกด้วยข้อมูลทั้งหมดถึง 30 พ.ย. 2011; ค่านี้เป็นการประเมินย้อนหลังของชุดฝึกใหม่ ไม่ใช่ holdout 3–30 พ.ย. ข้างต้น
